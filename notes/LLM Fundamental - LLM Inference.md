### 一、底层原理：一次大模型对话的三部曲

大模型生成文字的核心逻辑是 **自回归（Autoregressive）**——也就是说，它永远只能“根据前面的所有字，预测下一个字”。

把你的输入（Prompt）喂给模型后，内部会经历两个截然不同的阶段，中间靠 **KV Cache** 串联：

#### 1. Prefill（预填充阶段）：“一目十行看题干，顺便记笔记”
* **做什么**：把你输入的所有 Token（比如 2000 个字）**一次性全部送进模型**，让模型理解上下文，并吐出**第 1 个**输出 Token。
* **为什么能并行**：因为这 2000 个字已经是已知的、摆在桌面上的了。模型里的 Transformer 注意力机制（Attention）可以同时计算这 2000 个字之间的关系。
* **副产物（极其重要）**：在读这 2000 个字的过程中，模型每一层都会算出每个字对应的 **Key（键）** 和 **Value（值）** 向量（可以理解为模型读完这段话后记下的“浓缩笔记”）。系统会把这些向量存进显存里，这就是大名鼎鼎的 **KV Cache**。

#### 2. KV Cache（键值缓存）：“省得每次从头重读的笔记本”
* **如果没有 KV Cache 会怎样**：当模型吐出第 1 个字后，要预测第 2 个字时，必须把“原来的 2000 字 + 刚生成的第 1 个字”共 2001 个字**重新算一遍**；预测第 3 个字时，再重算 2002 个字……这会导致大量重复计算。
* **有了 KV Cache 之后**：前面 2000 个字的“笔记”已经保存在显存里了！算第 2 个字时，只需要算**刚生成的那个新字**，然后直接去翻 KV Cache 里的笔记做对比就行。
* **本质**：用**显存空间换计算时间**。这也是为什么上下文越长（比如 128K），显存占用越夸张的原因——因为“笔记本”越来越厚。

#### 3. Decode（解码阶段）：“一个字一个字地写答案”
* **做什么**：从生成第 2 个字开始，直到输出结束符（EOS），都属于 Decode 阶段。
* **怎么干活**：每一步只输入**上一步刚吐出来的那 1 个 Token**，结合显存里的 KV Cache，算出下一个 Token，然后把新 Token 的笔记追加写进 KV Cache 里，循环往复。
* **为什么慢**：因为必须先知道第 $N$ 个字，才能算第 $N+1$ 个字，天生是**串行**的，没法像 Prefill 那样一口气并行。

### 二、核心差异：为什么两个阶段的瓶颈完全不同？

这是理解现代大模型系统架构**最关键**的一点。GPU 有两个核心指标：**算力（FLOPS，每秒能做多少次乘法）** 和 **显存带宽（Memory Bandwidth，每秒能从显存搬多少数据到计算核心）**。

* **Prefill 是 Compute-bound（算力密集型 / 算力受限）**
  * **比喻**：就像大厨一次性切 1000 颗土豆。每次把“菜刀（模型权重）”从架子上拿下来，可以一口气切完 1000 颗土豆，**搬运工具的开销被摊薄了，真正决定快慢的是大厨切菜的手速（GPU 算力）**。
  * **特征**：并行度极高，GPU 利用率能拉满。这也是你上一篇微信文章里说的：把多条 Trigger 合并塞进 Prefill，只要算力还没顶满，耗时增长就很慢。

* **Decode 是 Memory-bound（访存密集型 / 显存带宽受限）**
  * **比喻**：每次只来 1 颗土豆。大厨需要把几十 GB 的“整套模型权重 + 越来越厚的 KV Cache 笔记本”从显存搬到计算核心里，结果**只为了算这 1 个新字**。算完这 1 个字，下一轮又得把几十 GB 权重重新搬一遍！
  * **特征**：GPU 的计算核心大部分时间都在**发呆等数据搬运**，算力利用率极低，真正卡脖子的是**显存带宽**。

#### 对应到用户体验的两个核心指标：
1. **TTFT（Time To First Token，首字延迟）**：从你发完问题，到屏幕上蹦出第 1 个字的时间。**主要由 Prefill 决定**。
2. **TPOT / ITL（Time Per Output Token，每字耗时 / 吐字速度）**：第 1 个字出来后，后面每个字往外蹦的间隔时间。**主要由 Decode 决定**。

### 三、现代 LLM 推理体系架构的五大经典优化

正因为 Prefill 和 Decode 性格完全相反（一个吃算力、一个吃带宽；一个怕没算力、一个怕显存不够/被插队），近两年的主流推理框架（如 vLLM、SGLang、TensorRT-LLM 等）基本都在围绕以下 5 个技术演进：

#### 1. Continuous Batching（连续批处理）—— 解决“等慢车”问题
* **老办法（Static Batching）**：凑齐 8 个请求一起推理，必须等最长的那个写完（比如写 1000 字），写完 50 字早早结束的人也得干等着，浪费算力。
* **新办法**：按每一步（Token 级别）动态调度。只要 8 个人里有一个人输出了结束符，立刻把他踢出队列、返回结果，同时**立刻塞一个新用户的请求进来接替他的位置**，让 GPU 流水线永远不停转。

#### 2. PagedAttention（分页注意力）—— 解决 KV Cache 显存碎片
* **痛点**：以前要预先给每个用户分配一块连续的显存来存 KV Cache（比如按最大长度 4096 分配），但用户可能只聊了 100 字，剩下的空间就白白浪费了，显存很快被占满，能同时服务的人数（并发度）上不去。
* **解法（vLLM 的成名技）**：借鉴操作系统的**虚拟内存分页（Paging）**机制。把 KV Cache 切成固定大小的“小格子（Block）”，不必在物理显存上连续存放，用多少页就动态申请多少页。显存利用率直接翻倍，并发量大幅提升。

#### 3. PD 分离（Prefill-Decode Disaggregation）—— 最前沿的集群架构
* **痛点**：如果把 Prefill 和 Decode 放在同一张 GPU 上混跑，会**互相干扰**。比如有 50 个用户正在顺畅地看模型吐字（Decode），突然第 51 个人发来一篇 5 万字的论文做 Prefill——这张卡的算力瞬间被这 5 万字占满，那 50 个人的屏幕就会突然“卡住”（吐字延迟飙升）。
* **解法**：把集群拆成两拨专职机器：
  * **Prefill 节点（算力型）**：专门负责读长输入、算出 KV Cache，算完第 1 个字后，通过高速网络（如 NVLink / RDMA）把 KV Cache 传给 Decode 节点。
  * **Decode 节点（大显存/高带宽型）**：专门稳稳当当地给用户吐字，不被突发长输入打断。
  * *(注：如果是单机部署，类似思路叫 **Chunked Prefill（分块预填充）**——把 5 万字切成 50 块，每块插在 Decode 间隙里悄悄算完，同样避免卡顿。)*

#### 4. Prefix Caching（前缀缓存 / Context Caching）—— 连 Prefill 都省了
* **痛点**：很多场景下，每次请求的开头一大段都是一样的（比如几千字的 System Prompt、代码库上下文、或者多轮对话的历史记录）。
* **解法**：把公共前缀的 KV Cache 缓存在显存甚至内存/SSD 里。下次再遇到相同前缀的请求，直接复用现成的 KV Cache，**跳过这一段的 Prefill 计算**，TTFT（首字延迟）瞬间降到极低，成本也大幅下降。

#### 5. Speculative Decoding（投机采样）—— 给串行的 Decode 提速
* **痛点**：既然 Decode 每次只算 1 个字太浪费显存带宽，能不能一次算好几个字？
* **解法**：找一个极快的小模型（或者特制的草稿头，如 DeepSeek 的 MTP 多 Token 预测）一口气**猜**出接下来的 4~5 个字；然后让大模型像做 Prefill 一样，**并行一次**把这 5 个字全部验证一遍。猜对的直接采纳，猜错的从错误位置重新生成。这样把原本“搬 5 次模型权重算 5 个字”，变成了“搬 1 次权重验证 5 个字”，在不损失准确率的前提下大幅提升吐字速度。

### 一句话总结整张架构图

> **Prefill** 是一口吃成胖子的**算力游戏**（决定首字响应有多快），**Decode** 是一步一个脚印的**带宽游戏**（决定吐字有多丝滑），**KV Cache** 是它们之间沉甸甸的**记忆桥梁**；而整个现代 LLM 推理工程，本质上就是在**算力、显存容量、显存带宽**这三者之间不断做切分、复用和动态调度。
